# Reflection, effect-open-protocol (2026-09-17, claude)

## Summary

Delivered an Open Protocol client written only with Effect: codec, supervised
connection, result delivery with acknowledgement after the handler, gap
recovery, device pool, TCP and in-memory transports, a fault-injecting
simulator and a chaos demo. Shipped as PR #1, mergeable, with a clean-clone run
of install, check, test, build and demo. The work went well; what it taught me
is mostly about which kind of test finds which kind of bug.

## Tooling experience

**Worked.** The packet structure paid for itself at the P0 design stop: the
user answered ten protocol questions in one round, and two of those answers
("an unacknowledged result is lost", "the controller queues until ACK")
reshaped the design before any code existed. Having `.repos/effect` on disk
meant API questions were answered by reading source rather than guessing, once
I remembered to look. `@effect/vitest` with `TestClock` made keep-alive,
backoff and timeout behaviour testable in milliseconds of real time, which is
the single biggest difference from how this code would have been tested
otherwise.

**Didn't.** My first instinct for Effect v4 API names was wrong often enough to
be a pattern, not an accident: v3 shapes are apparently strong priors. The
`Effect.retry` plus `Schedule.upTo` polling loop hanging cost a debugging
detour that ended in rewriting the loop by hand.

**Frustrating.** Three separate debugging sessions ended at the same root
cause shape: something was silently dropped and nothing failed. A result pushed
into a closed socket, a session cleaning up after its replacement, a baseline
recorded when a request failed. None of these produced an error; they produced
a smaller number at the end of a demo run. That is the expensive kind of bug in
this domain, and it is exactly what the chaos test is for.

**Wished existed.** A way to assert "no fiber is still alive under this scope"
after close. I tested shutdown by observing the simulator losing its
subscription, which is indirect. A direct assertion on released resources would
be stronger evidence for the "no resources left open" requirement.

## Implementation improvement opportunities

- Dedup and the recovery watermark are in memory. Persisting the watermark
  before acknowledging would close the restart window that the README currently
  documents as a limit.
- Gap recovery is bounded by `recoveryLimit` and skips the remainder with a log
  line. A device offline for a long time therefore needs manual reconciliation.
  An explicit "recovery incomplete" signal on the connection state would be
  better than a log.
- The codec parses fixed offsets in plain functions returning `Result` instead
  of schema transformations. That was a deliberate call for clarity on a
  fixed-width ASCII protocol, and it deserves an ADR that does not yet exist.
- `DevicePool.status` collects per-device state on demand. An aggregate stream
  of changes would serve a dashboard better, and was cut for scope.

## Goal and prompt critique

The GOAL launcher was clear about the stop condition, which mattered: the
design gate worked exactly as intended. Two revisions I would make:

1. The acceptance criteria named the demo as evidence for "zero lost". That
   shaped the order of work, and the demo came first. Naming a test instead
   would have pulled the chaos invariant forward by three phases, where it
   would have caught the delivery and recovery defects as they were written.
2. The SPEC inherited "no-gos" from the brief, including scale-out analysis as
   a documentation deliverable. That deliverable was later cut by the user
   because it advertised something unimplemented. A packet should distinguish
   between what the work excludes and what the documentation should say about
   the exclusion.

## TODOs worth codifying

- A standard: a packet claiming a runtime invariant ships a test asserting that
  invariant in the phase that introduces it. Demos are for humans, tests are for
  regressions.
- A note in the Effect guidance: check `Flag`, `Schedule` and `Effect` option
  names in `.repos/effect` before writing them. The v3 to v4 renames are dense
  enough that priors are unreliable.
- The `Effect.retry` plus `Schedule.upTo` hang, reduced and reported.

## Lessons (confidence-tiered)

- **HIGH, Critical:** Write the invariant test in the phase that creates the
  invariant. Six phases of green unit tests coexisted with three data-loss bugs
  in this packet, and the first chaos run found all three.
- **HIGH, Critical:** Test against the real resource at least once. The
  in-memory transport could not express the rule that leaked sockets, so only
  a real socket could find it.
- **MEDIUM, Best practice:** When a system can silently drop work, make the
  drop observable before debugging it. Adding a single log line to the
  simulator's push path turned three guesses into one measurement.
- **MEDIUM, Best practice:** Verify library APIs against installed source
  rather than recall, in a fast-moving ecosystem. The same applies to the
  protocol: reading the specification PDF corrected several details that the
  plan had marked "to verify".
- **LOW, Consideration:** A demo that judges itself while work is still in
  flight will lie. The quiet phase before measurement was not in the plan and
  turned out to be necessary.
